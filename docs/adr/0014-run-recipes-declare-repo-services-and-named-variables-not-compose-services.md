# Run recipes declare Repo services and the variables they read, not compose services

ADR 0004 made a Run recipe a compose file (`.weave/compose.yaml`) with the workflow's own fields in an `x-weave:` block, and ADR 0012 promised that recipe would not change whichever Environment read it. ADR 0013 then put every Story's software inside the Product agent server, which has no container runtime, and made databases something the Product provides (Branched on Dolt/Doltgres, or Shared), not something a recipe starts. Most of a compose file would then mean nothing: images, builds, port mappings and database services would be silently ignored, and running the file by hand would give a developer containers and bundled databases that agent runs never use. We therefore replace it with a workflow-owned file, `.weave/run.yaml`, that lists **Repo services** as commands: `setup`, a long-running `start` that listens on `$PORT`, and a `ready` check (an HTTP path, a TCP check or a command). The existing `x-weave` fields keep their names and meaning at the file's top level (`depends_on`, `secrets`, `seed`, `databases`, `external_mcp`), and `migrate` joins `seed`. Every address a Repo needs reaches it as an environment variable whose name the recipe chooses: a database by logical name and kind with the variable the app already reads (`{name: main, kind: postgres, url_env: DATABASE_URL}`), and a sibling Repo's service the same way (`{repo: sri-aurobindo-works-chat, service: api, url_env: CHAT_API_URL}`). The Product config, not the recipe, decides whether each named database is Branched or Shared and where it is.

## Considered Options

- **Keep `.weave/compose.yaml` and run each service's `command` as a process** — no new format and PR #64 stays nearer intact, but half the file is dead in Phase 1 and the file run by hand behaves differently from agent runs.
- **Fixed workflow variable names (`WEAVE_DB_MAIN_URL`, `WEAVE_<REPO>_<SERVICE>_URL`)** — uniform, but every Repo must change its startup to translate them into the names its code already reads.
- **Skip `setup` when declared input files are unchanged since the Story's last bring-up** — faster for slow installs, but it is workflow-side bookkeeping, and a wrong input list leaves an agent running a stale build without knowing.
- **Leave Shared databases' variables unset during `migrate` and `seed`** — simpler, but many apps load all their config at import and would crash while migrating only their Branched database.

## Consequences

- Bring-up, per Repo in dependency order: `setup` → `migrate` → `start` → wait for `ready` → `seed`. Each runs at every bring-up, that is, at the start of every run of the Story and whenever the agent restarts a Repo service through `weave-env`; making them cheap when nothing changed is the Repo's job, as ADR 0011 already makes it for seeding. The workflow tracks nothing.
- The Product agent server keeps one package cache folder per Product on a volume mounted at setup, and the shared base image points the standard cache variables (`PIP_CACHE_DIR`, `UV_CACHE_DIR`, `npm_config_cache`, …) at it, because per-run home folders (Spec 2.1) would otherwise throw caches away after every run. Installed dependencies (`.venv`, `node_modules`) stay in the Story workspace, so only a Story's first bring-up installs in earnest. Every Story of the Product shares the cache, which adds no exposure ADR 0013 has not already accepted.
- One `$PORT` per Repo service, assigned per (Story, Repo, service) and kept for the Story's life.
- During `migrate` and `seed`, a Shared database's variable points at read-only credentials (the ones its read-only Environment MCP server uses), so a write to it fails loudly; a database kind that cannot give read-only credentials (e.g. Neo4j Community) has its variable unset during those two steps. `setup` and `start` get the normal credentials.
- The variables a run's recipes choose (databases and sibling services) are also set in the agent's own environment, since tests and Proofs need them as much as running services do; `weave-env status` lists every Repo service's URL. Two recipes in one run that give the same variable different values stop the run as `needs-setup`, naming both Repos.
- Environment MCP servers are wired from the same values the Repo's variables carry, so they always reach the database the app reaches.
- PR #64's compose handling (services as containers, `seed.service`, `databases[].service` and literal credentials) is replaced; its parsing of the other fields and its tests carry over. Spec 2c, when it returns, decides how to box each Repo service rather than reading images from the recipe.
- Amends ADR 0004 (the recipe as a compose file) and ADR 0012 (the recipe unchanged between Environments).
